Konsekuensi untuk rencana: **menaikkan volume publish tidak akan menaikkan trafik** selama jalur
submit/crawl tidak diperbaiki. Prioritas = indexasi, bukan produksi.

**.my**: **tepat 40/hari**, stabil 8 hari berturut-turut (17–24 Sep, terukur dari `posts_meta`

- 400 URL baru/hari dari satu domain dengan otoritas rendah = sinyal spam klasik;
- kuota indexasi (GSC Indexing API 200/hari, IndexNow terbatas) tidak mungkin menutup 400 URL;
- tiap artikel baru ikut menaikkan biaya query `posts_meta` / `posts_content`.

**Keputusan user (final):** turunkan ke **10–15 artikel berkualitas/hari**, bukan memangkas yang sudah terbit.

### 8.1b Empat pemborosan spesifik (baru teridentifikasi saat re-verify)
| # | Query | Kenapa boros | Fix |
|---|---|---|---|
| A | #1 | memakai **`status='pending' OR (status IN …)`** → planner tidak bisa pakai index → SCAN | tulis ulang jadi **satu** `status IN (…)`; hilangkan `OR` antar-status |
| B | #2 | sudah `IN (…)` tetapi **`url LIKE 'https://…%' OR url LIKE …`** tidak bisa di-index, dan `ORDER BY CASE …` memaksa sort | simpan kolom `host`/`domain` terpisah (bukan LIKE pada URL) + index `(status, host, gsc_submitted_at)` |
| C | #5 | `COUNT(*) WHERE status=?` membaca **377.883 baris** untuk satu angka (efficiency 0,0000026) | `CREATE INDEX … ON keyword_queue(status)` — atau hitung di Postgres setelah Fase 2 |
| D | #4 & #6 | `ORDER BY iso_date DESC` / `SELECT url` **tanpa `LIMIT`** → seluruh tabel dibaca tiap kali (16.341 dan 16.684 baris/run) | tambahkan `LIMIT`; #3 (`generated_drafts`) juga 51×/hari tanpa LIMIT |

Catatan: query #3, #4, #6 punya efficiency ≈ 1,0 — artinya **bukan** query rusak, melainkan
"dipanggil terlalu sering tanpa batas". Karena itu perbaikannya `LIMIT` + cache, bukan index.

### 8.2 Kenapa 3 query itu mahal
Query `pending_indexing` di `worker-entry.js` sekitar **baris 7018–7022** memakai pola:
```sql
… WHERE (status = 'pending' OR status = 'retry') AND … ORDER BY … LIMIT …
```
Klausa `OR` pada kolom yang sama **membatalkan pemakaian index** → SQLite memilih SCAN.
**Ukuran tabelnya kecil — masalahnya frekuensi scan.** Terukur ulang 24 Sep (sore):
`pending_indexing` = **17.026 baris** (`pending` 16.754 · `gsc_submitted` 264 · `indexed` 8).
Angka "3,8 juta baris" yang beredar di dokumen lama **salah** dan sudah dikoreksi di sini.

Matematikanya: query terberat membaca **2.483.010 rows dalam 51 run** = **±48.687 rows/run**
≈ **2,9× full-scan** tabel 17 ribu baris setiap run. Jadi 69% kuota D1 harian habis bukan karena
tabelnya raksasa, melainkan karena **scan penuh diulang-ulang tanpa index**. Konsekuensi penting:
**Fix A (index + `status IN (…)`) saja sudah menyelesaikan ~69% beban** — menghapus baris (Fase 5.2)
hampir tidak memberi efek karena hanya ada 272 baris non-`pending`.

### 8.3 Perbaikan bertingkat
| Tingkat | Aksi | Efek |
|---|---|---|
| Segera | ganti `(status='pending' OR status='retry')` → `status IN ('pending','retry')` + index `(status, created_at)` | SCAN → SEARCH |
| Segera | backlog `pending_indexing` **dipindah ke Postgres VPS**; D1 hanya simpan ≤ 5.000 baris aktif | −95% rows read |
| Struktural | semua read artikel pindah ke R2 (object per artikel) | D1 tidak lagi di jalur serve |
| Guard | `EXPLAIN QUERY PLAN` wajib SEARCH sebelum query baru di-deploy (sudah jadi aturan di ../AGENTS.md) | cegah regresi |

Verifikasi wajib setelah deploy:
```bash

# target: avgRowsRead per query < 1.000; total < 200.000/jam
```
Catatan gotcha: `wrangler d1 insights` **tidak punya flag `--remote`**; field hasil adalah
`avgRowsRead` / `totalRowsRead` / `queryEfficiency` (bukan `rowsRead`).

   tanpa deploy ulang.
6. **Static fallback tetap ada** (by design) supaya situs tidak mati saat R2/VPS bermasalah — tapi
   fallback itu yang menyebabkan soft-404 (§10.2), jadi harus dikombinasikan dengan **404 jujur**
   untuk slug yang benar-benar tidak ada di mana pun.

### 12.4 Kenapa bukan "pindah semua ke Pages static"
Dijawab oleh §10.2: 9.373 soft-404 + headroom 9.822 file yang akan habis dalam ±1 bulan.
Pages tetap dipakai untuk `.my` (1.337 URL) dan sebagai fallback co.id, bukan sebagai jalur utama co.id.

## 14. Keamanan & hygiene

| # | Temuan | Risiko | Tindakan |

| 1 | **Groq API key plaintext** di `../plan.md` yang ter-track git | key bocor ke riwayat repo | **rotate key sekarang**, hapus dari file, tambah `../plan.md` ke `.gitignore` atau ganti ke placeholder `$GROQ_API_KEY` |

## 16. Risiko & mitigasi

| Risiko | Pemicu | Dampak | Mitigasi |
|---|---|---|---|
| **Kehilangan artikel** saat migrasi D1 → R2/Postgres | cutover big-bang, DELETE prematur | permanen, tak terpulihkan | dual-read, hitung 3-arah, backup `d1 export` sebelum tiap fase, larangan DELETE (§12.3) |
| D1 quota lock (error 7500) berulang | query SCAN `pending_indexing` | situs jatuh ke static fallback → 9.373 soft-404 | fix §8.3 + pindahkan backlog ke Postgres |
| Soft-404 massal di-index Google | Pages jadi jalur utama | penurunan kualitas situs | Worker + R2 jalur utama; 404 jujur untuk slug tak dikenal |
| Cap 20.000 file Pages | static-first co.id | deploy gagal | jangan static-first co.id |
| Klaim palsu "build OK" | rsync tak terverifikasi | rencana berdiri di atas fondasi kosong | wajib bukti `find dist/blog | wc -l` (§9.5) |
| Publish spike dinilai spam | 400/hari | penalti kualitas | turunkan ke 10–15/hari, jangan hapus yang lama |
| Rahasia bocor | token di `wrangler.jsonc`, key di `../plan.md` | akses admin/GSC disalahgunakan | §14: rotate + secret + sweep diff |
| Cron slot habis (cap 5/account) | menambah cron baru ke `wrangler.jsonc` | error 10072, deploy sebagian gagal | pakai time-gate hourly, jangan tambah slot |
| Growth loop tetap mati | `GSC_SITE_URL` tak diganti | enrich/ctr-fix 0 kandidat | ganti ke `sc-domain:` lalu verifikasi rank-sync |
